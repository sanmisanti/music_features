\section{Visión General de la Arquitectura}
\label{sec:vision-general}

El sistema propuesto integra información acústica y semántica de canciones para generar recomendaciones que consideren tanto las propiedades sonoras de cada canción como el contenido de sus letras. La arquitectura se organiza como un pipeline secuencial de cinco etapas.

La primera etapa carga, valida y caracteriza el catálogo de canciones disponible, documentando sus propiedades estadísticas y los sesgos preexistentes. La segunda etapa genera las representaciones numéricas de cada canción en dos espacios complementarios: por un lado, vectores semánticos de 384 dimensiones que capturan el significado de las letras mediante un modelo de lenguaje preentrenado; por otro, un vector de 13 descriptores acústicos que describe las propiedades sonoras. La tercera etapa aplica técnicas de clustering sobre ambas representaciones para identificar agrupaciones naturales en el catálogo. La cuarta etapa construye el sistema de recomendación propiamente dicho, combinando las señales de ambos espacios mediante una estrategia de fusión ponderada. Finalmente, la quinta etapa evalúa el sistema.

Las decisiones de diseño en cada etapa están condicionadas por las propiedades del dataset fuente, cuya caracterización se presenta a continuación.

\section{Pipeline de Datos}
\label{sec:pipeline-datos}

La calidad de un sistema de recomendación está condicionada por las propiedades de los datos sobre los que opera. Antes de aplicar cualquier transformación o filtrado, resulta necesario caracterizar el dataset fuente de forma exhaustiva: comprender qué información contiene, cuánta es utilizable, qué sesgos presenta y qué limitaciones impone. Esta caracterización fundamenta las decisiones de diseño y permite documentar explícitamente la pérdida de datos (cuántos registros se excluyen en cada etapa y por qué razón).

\subsection{Fuentes de Datos}
\label{subsec:fuentes}

La evaluación experimental del sistema requiere un dataset que contenga simultáneamente features acústicas y letras para un conjunto suficientemente grande de canciones. Se consideraron dos alternativas: construir un dataset propio mediante las APIs de Spotify y Genius, o utilizar un dataset público existente. La construcción de un dataset propio ofrecería mayor control sobre la composición del catálogo, pero enfrenta un obstáculo técnico decisivo: los endpoints de features de audio de la Web API de Spotify fueron deprecados el 27 de noviembre de 2024 \parencite{spotify_2024_web_api}. Sin estas features no es posible construir el componente musical del sistema, con independencia de que las letras sí puedan obtenerse por otras vías. Por esta razón, el trabajo opta por utilizar un dataset público preexistente que recopiló las features mientras el acceso aún estaba disponible e integra ambas fuentes de información.

El dataset utilizado en este trabajo es una compilación pública disponible en Kaggle \parencite{nakhaee_2020_spotify_lyrics} que integra dos fuentes de información complementarias. La base del dataset proviene del proyecto TidyTuesday, que recopiló las propiedades acústicas de aproximadamente 30\,000 canciones mediante la Web API de Spotify \parencite{spotify_2024_web_api}. Sobre esa base, \textcite{nakhaee_2020_spotify_lyrics} enriqueció el dataset con dos elementos adicionales: las letras completas de cada canción, obtenidas mediante el paquete \texttt{genius} de R (que extrae las letras por scraping de las páginas de Genius), y la detección automática del idioma de cada letra, realizada con la librería langdetect de Python. El proceso de obtención de letras produjo una pérdida de aproximadamente el 50\% del dataset original (canciones para las cuales Genius no disponía de letras), resultando en 18\,454 registros y 25 columnas que se organizan en tres categorías: metadatos de la canción y su contexto en playlists, 12 features acústicas numéricas y el texto completo de las letras.

\input{tables/dataset_overview}

El Cuadro~\ref{tab:dataset_overview} resume las propiedades generales del dataset. No existen identificadores de pista duplicados y los valores faltantes genuinos se concentran en dos columnas: letras (252 registros) e idioma (260 registros). Un análisis cruzado de los 252 registros sin letras con su valor de \textit{instrumentalness} revela que el 67.5\% (170 canciones) presenta un valor superior a 0.5 (el umbral que Spotify utiliza para clasificar una canción como probable instrumental), con una media de 0.60 y una mediana de 0.77, frente a una media de 0.04 para las canciones con letras. Esto confirma que la mayoría de las canciones sin letras son efectivamente instrumentales. El 32.5\% restante (82 canciones) presenta \textit{instrumentalness} baja (lo que indica que Spotify detecta presencia significativa de vocales en la señal de audio) pero carece igualmente de letras en Genius. La inspección manual de estos casos revela que se trata predominantemente de tracks de música electrónica de artistas como Martin Garrix o Vicetone, un subdominio donde la cobertura de Genius es limitada: las vocales existen en la grabación, pero nadie ha transcrito las letras en la plataforma. De hecho, EDM concentra el 46\% de todas las canciones sin letras (116 de 252), lo cual es coherente con la naturaleza del género. Los 260 valores faltantes de idioma incluyen las 252 canciones sin letras (donde langdetect no puede operar) más 8 canciones cuyo texto resultó demasiado breve o ambiguo para la detección automática. La cobertura de letras (98.63\% de los registros) es alta, lo que permite que la gran mayoría de las canciones sean procesables por el componente semántico del sistema.

Las canciones del dataset están organizadas en 6 géneros musicales y 24 subgéneros, derivados de las playlists de Spotify de las que fueron extraídas. Cada canción pertenece a exactamente un género y un subgénero, lo que proporciona una referencia que, si bien no constituye un ground truth de clasificación musical absoluto, resulta útil como etiqueta proxy para evaluar la coherencia de las agrupaciones producidas por el clustering.

\subsubsection*{Features acústicas}

Las 12 features acústicas que Spotify calcula para cada canción capturan propiedades perceptuales y técnicas de la señal de audio. Estas features se agrupan en tres categorías según su naturaleza y escala:

\begin{itemize}[leftmargin=2em]
    \item \textbf{Índices perceptuales normalizados} (escala 0--1): \textit{danceability} estima qué tan bailable es una canción, considerando tempo, estabilidad rítmica y fuerza del ritmo. \textit{Energy} es una medida perceptual de intensidad y actividad: los valores altos corresponden a canciones que se perciben rápidas, intensas y enérgicas, mientras que los valores bajos reflejan piezas más calmas. \textit{Speechiness} detecta la presencia de voz hablada (valores altos indican podcasts). \textit{Acousticness} estima la probabilidad de que la grabación sea acústica. \textit{Instrumentalness} predice si la canción carece de contenido vocal. \textit{Liveness} detecta la presencia de audiencia en la grabación. \textit{Valence} cuantifica la positividad de la canción: los valores altos se asocian a un tono alegre, mientras que los valores bajos reflejan un carácter más triste.

    \item \textbf{Propiedades musicales}: \textit{key} identifica la tonalidad (0 = Do, 1 = Do\#, \ldots, 11 = Si). \textit{Mode} indica la modalidad (0 = menor, 1 = mayor). \textit{Tempo} es la velocidad en BPM. \textit{Duration\_ms} es la duración en milisegundos.

    \item \textbf{Medición técnica}: \textit{loudness} mide el volumen promedio en decibelios (típicamente entre $-60$ y 0~dB).
\end{itemize}

\subsubsection*{Contenido lírico}

El campo de letras almacena el texto completo de cada canción como una cadena de caracteres. De los 18\,454 registros, 18\,202 (98.63\%) contienen letras válidas (no nulas y con contenido textual). Los 252 registros restantes carecen de letras a pesar de haber sobrevivido el filtrado inicial por disponibilidad en Genius, lo que sugiere que corresponden a canciones instrumentales, entradas con letras vacías en Genius, o errores puntuales en el proceso de scraping.

Antes de aplicar cualquier filtrado o transformación al dataset, es necesario identificar los sesgos que ya están presentes en los datos fuente. Estos sesgos condicionan la generalización de los resultados y la interpretación de las métricas de evaluación.

\textbf{Balance de género musical.} El dataset contiene 6 géneros con una distribución razonablemente equilibrada (Figura~\ref{fig:genre_distribution}). Pop es el género más representado (3\,993 canciones, 21.6\%) y EDM el menos representado (2\,045, 11.1\%), una diferencia de factor 1.95$\times$ entre el mayor y el menor. \textbf{Sesgo lingüístico.} La distribución de idiomas revela un sesgo marcado (Figura~\ref{fig:language_distribution}): el 83.5\% del dataset corresponde a canciones en inglés, seguido por español con 9.2\% y 33 idiomas adicionales que en conjunto representan el 7.3\% restante. En primer lugar, el modelo de vectorización semántica está diseñado para operar en más de 100 idiomas, pero su rendimiento puede variar según la representación de cada idioma en sus datos de entrenamiento. En segundo lugar, dado que el inglés es el idioma ampliamente dominante, el componente semántico opera y se evalúa principalmente sobre contenido en este idioma, que constituye la mayor parte del catálogo.

\subsection{Preprocesamiento y Selección}
\label{subsec:preprocesamiento}

El análisis exploratorio presentado en la sección anterior identifica varias propiedades del dataset que requieren tratamiento antes de proceder a la vectorización. El preprocesamiento aplica una secuencia de filtros de calidad diseñados para eliminar únicamente los registros que no pueden ser procesados de forma significativa por las etapas posteriores del pipeline.

Se aplican tres filtros en secuencia, cada uno operando sobre el resultado del anterior:

\begin{enumerate}[leftmargin=2em]
    \item \textbf{Letras nulas o vacías.} Se eliminan los 252 registros (1.37\%) que carecen de contenido textual. Sin letras, el componente semántico del sistema no puede generar una representación para la canción, lo que la hace inutilizable para la mitad de la arquitectura propuesta.

    \item \textbf{Letras con menos de 10 palabras.} Se eliminan 108 registros adicionales (0.59\%). Un texto de menos de 10 palabras (frecuentemente una frase aislada, un título repetido o un artefacto de scraping) no proporciona suficiente contexto semántico para que el modelo de embeddings genere una representación significativa.

    \item \textbf{Letras con más de 2\,000 palabras.} Se eliminan 130 registros (0.72\%). La canción musical típica contiene entre 200 y 500 palabras; letras que exceden las 2\,000 palabras son, en la práctica, artefactos de scraping (transcripciones duplicadas, contenido ajeno concatenado al texto de la canción, o errores de extracción de Genius). La inspección manual de estos casos confirma esta interpretación.
\end{enumerate}

Adicionalmente, se corrigen 4 valores de \textit{loudness} que exceden 0~dB (el máximo teórico para audio digital no clipeado) recortándolos a 0~dB. Esta corrección no elimina registros, sino que ajusta valores anómalos a su límite físico.

La pérdida total es de 490 registros (2.66\%), resultando en un dataset seleccionado de 17\,964 canciones con 25 columnas preservadas. Las 17\,964 canciones que superan el preprocesamiento constituyen el conjunto de trabajo para todas las etapas posteriores del pipeline.

\section{Componente Semántico: Vectorización de Letras}
\label{sec:componente-semantico}

El componente semántico del sistema transforma las letras textuales de cada canción en vectores numéricos que capturan su significado, permitiendo calcular similitudes temáticas entre canciones mediante operaciones algebraicas sobre estos vectores. Esta transformación se realiza mediante un modelo de lenguaje preentrenado que codifica el texto en un espacio de alta dimensionalidad donde la proximidad entre vectores refleja la similitud semántica entre los textos que representan.

% ---------------------------------------------------------------------------
% SUBSECCIÓN 5.3.1 — Selección del Modelo
% ---------------------------------------------------------------------------
\subsection{Selección del Modelo de Embeddings}
\label{subsec:seleccion-modelo}

El modelo seleccionado es \texttt{multilingual-e5-small}, un modelo de embeddings de texto desarrollado por Microsoft \parencite{wang_2022_e5}. E5 (\textit{EmbEddings from bidirEctional Encoder rEpresentations}) pertenece a la familia de modelos basados en la arquitectura Transformer \parencite{vaswani_2017_attention} y está diseñado específicamente para generar representaciones vectoriales de texto que sean útiles para tareas de búsqueda semántica, clasificación y clustering.

La selección de este modelo se fundamenta en cuatro propiedades relevantes para el proyecto:

\begin{enumerate}[leftmargin=2em]
    \item \textbf{Ventana de contexto.} El modelo procesa secuencias de hasta 512 tokens. Dado que la letra musical promedio del dataset genera 607 tokens, una ventana de este tamaño reduce la fracción de contenido que debe ser truncada o dividida para su procesamiento.

    \item \textbf{Soporte multilingüe.} El modelo soporta más de 100 idiomas. Aunque el 83.5\% del dataset está en inglés, el 16.5\% restante incluye canciones en español, alemán, portugués y otros 32 idiomas. Un modelo monolingüe descartaría la señal semántica de estas canciones o generaría representaciones degradadas.

    \item \textbf{Prefijo de tarea.} A diferencia de modelos genéricos, E5 utiliza un prefijo textual (\texttt{"passage: "}) que indica al modelo el tipo de tarea a realizar. Este mecanismo permite que el mismo modelo genere representaciones optimizadas para distintos propósitos sin reentrenamiento.

    \item \textbf{Dimensionalidad.} El modelo genera vectores de 384 dimensiones. Esta dimensionalidad mantiene acotado el costo computacional y de memoria de las operaciones de distancia que requieren el clustering y la búsqueda de vecinos más cercanos sobre las casi 18\,000 canciones del catálogo. Manteniéndolo dentro de la familia E5 para no resignar capacidad de representación.
\end{enumerate}

\subsection{Análisis de Cobertura de Tokens}
\label{subsec:cobertura-tokens}

Antes de vectorizar las letras, es necesario determinar qué fracción del contenido cabe dentro de la ventana de 512 tokens del modelo. El análisis exploratorio estimó esta cobertura en 58.8\% utilizando una heurística de 1.33 tokens por palabra (un ratio aproximado para texto en inglés). Sin embargo, el tokenizador real del modelo opera mediante un algoritmo de \textit{subword tokenization} que fragmenta las palabras en unidades menores cuando encuentra vocabulario infrecuente: slang, contracciones, palabras en idiomas con morfología compleja, y la ortografía no estándar frecuente en letras musicales generan más fragmentos por palabra de lo que sugiere la heurística.

\input{tables/token_coverage}

El Cuadro~\ref{tab:token_coverage} presenta los resultados de la medición con el tokenizador real del modelo. La cobertura efectiva es de 53.48\% (9\,607 de 17\,964 canciones dentro de la ventana), inferior a la estimación heurística. La distribución de tokens por canción tiene una media de 607, mediana de 486 y desviación estándar de 433, con un rango amplio: desde 16 tokens (letras extremadamente breves) hasta 4\,104 tokens (letras extensas que exceden la ventana por un factor de 8).

Que el 46.52\% de las canciones exceda la ventana de contexto plantea un problema metodológico concreto: si estas letras simplemente se truncan a 512 tokens, el sistema descartaría toda la información semántica posterior a ese punto. Dos canciones con contenido temático idéntico pero distinta longitud podrían producir embeddings diferentes (no por una diferencia semántica real, sino por un artefacto del pipeline). Este sesgo sistemático por longitud debe evitarse.

% ---------------------------------------------------------------------------
\subsection{Estrategia de Chunking}
\label{subsec:chunking}

Para eliminar la pérdida de información por truncamiento, se implementa una estrategia de \textit{chunking} (división del texto en fragmentos solapados) con agregación por promedio. El procedimiento opera de la siguiente manera:

\begin{enumerate}[leftmargin=2em]
    \item \textbf{División en chunks.} Cada letra que excede la capacidad del modelo se divide en fragmentos de 450 tokens de contenido. El modelo necesita 5 tokens adicionales de overhead (3 tokens para el prefijo de tarea \texttt{"passage: "} y 2 tokens especiales que delimitan el inicio y fin de la secuencia), por lo que cada fragmento utiliza 455 de los 512 tokens disponibles. Los fragmentos consecutivos comparten 50 tokens de solapamiento, lo que produce un avance efectivo de 400 tokens entre fragmentos. Este solapamiento preserva la continuidad semántica en las fronteras: una oración que cae en el límite entre dos fragmentos es procesada completa por al menos uno de ellos.

    \item \textbf{Codificación independiente.} Cada fragmento se procesa por el modelo de forma independiente, generando un vector de 384 dimensiones por fragmento.

    \item \textbf{Agregación por promedio.} Los vectores de todos los fragmentos de una canción se combinan mediante un promedio aritmético simple, y el vector resultante se re-normaliza a norma L2 unitaria. Esta normalización garantiza que todos los vectores del dataset (tanto los de canciones cortas que no requirieron chunking como los de canciones largas procesadas en múltiples fragmentos) habiten en la misma hiperesfera unitaria, lo que permite calcular similitudes.
\end{enumerate}

Las canciones cuyas letras generan 507 tokens o menos (los 512 de la ventana menos los 5 de overhead) caben completas en la ventana y pasan directamente al modelo sin división. El resultado es que el 53.3\% de las canciones (9\,583) se procesa sin chunking y el 46.7\% restante (8\,381) se divide en múltiples fragmentos, generando un total de 32\,303 chunks con un promedio de 1.80 chunks por canción (2.71 chunks por canción entre las que requieren división).

El proceso de vectorización completo produce una matriz de embeddings de dimensiones $17\,964 \times 384$ en formato float32, con norma L2 media de 1.0000, cero vectores nulos, cero valores NaN, y cero dimensiones muertas (dimensiones donde todos los vectores tienen el mismo valor). La cobertura del contenido semántico es ahora del 100\%, ninguna canción pierde información por truncamiento.

\section{Componente Musical: Features Acústicas}
\label{sec:componente-musical}

Las 12 features acústicas de Spotify requieren dos transformaciones antes de poder utilizarse en algoritmos basados en distancia euclidiana: una codificación adecuada de la variable categórica circular \textit{key}, y una normalización de escala que iguale la contribución de todas las features.

\subsection{Codificación circular de la tonalidad}
\label{subsec:codificacion-circular}

La feature \textit{key} codifica la tonalidad de cada canción como un número entero entre 0 (Do) y 11 (Si). El inconveniente es que las tonalidades no se ordenan a lo largo de una recta, sino que forman un ciclo, como las horas en la esfera de un reloj: después de Si (11) la escala regresa a Do (0). Por eso Si y Do son tonalidades vecinas, aunque como números (11 y 0) sean los más alejados de toda la serie. Si se usara el entero tal cual en un cálculo de distancia, el algoritmo concluiría que Do sostenido (\textit{key} = 1) se parece a Re (\textit{key} = 2) pero no a Si (\textit{key} = 11), cuando musicalmente Si y Do están pegados. Aplicar \textit{z-score} sobre el entero conservaría esa relación falsa.

La solución es ubicar cada tonalidad sobre un círculo en lugar de sobre una recta, de modo que el 11 y el 0 queden literalmente uno al lado del otro. Esto se logra con la codificación circular descrita en el Marco Teórico (Ecuación~\ref{eq:circular-teo}): las doce tonalidades se reparten de forma equiespaciada sobre la circunferencia, y la posición de cada una se describe con dos coordenadas, \textit{key\_sin} y \textit{key\_cos} (su altura vertical y su desplazamiento horizontal sobre el círculo). Hacen falta dos valores en lugar de uno porque un único número no basta para señalar un punto sobre una circunferencia.

Con esta representación, cada tonalidad ocupa una posición equidistante sobre el círculo y la distancia entre dos de esos puntos refleja su verdadera proximidad armónica. Do (\textit{key} = 0) y Si (\textit{key} = 11), que como enteros parecían los extremos opuestos de la serie, quedan ahora tan cerca como cualquier otro par de tonalidades consecutivas.

La feature \textit{mode} (modalidad, valores 0 o 1) es binaria, se normaliza directamente con \textit{z-score} sin requerir tratamiento especial.

\subsection{Normalización \textit{z-score}}
\label{subsec:normalizacion-zscore}

Las features acústicas operan en escalas heterogéneas: los índices perceptuales varían entre 0 y 1, \textit{loudness} se mide en decibelios ($-34$ a 0~dB), \textit{tempo} en BPM (37 a 214), y \textit{duration\_ms} en milisegundos (31\,893 a 517\,810). Si estas features se utilizan directamente en algoritmos como K-Means o el enlace de Ward, las features con mayor rango numérico dominarían el cálculo: \textit{duration\_ms}, con valores del orden de $10^5$, contribuiría desproporcionadamente más que \textit{danceability}, con valores entre 0 y 1, independientemente de su relevancia para el agrupamiento.

Para igualar la contribución de cada feature, se aplica la normalización \textit{z-score} sobre las 13 features resultantes (incluyendo \textit{key\_sin} y \textit{key\_cos}), tomando la media y la desviación estándar de cada feature calculadas sobre las 17\,964 canciones del dataset seleccionado. Tras la transformación, todas las features comparten la misma escala y centro, lo que permite que el algoritmo de clustering las pondere de forma equitativa.

\section{Unificación de Representaciones}
\label{sec:unificacion}

Las dos secciones anteriores producen representaciones complementarias para cada canción: un vector semántico de 384 dimensiones que captura el significado de las letras, y un vector musical de 13 dimensiones que describe las propiedades acústicas. Ambas representaciones están alineadas (por su \texttt{track\_id}) pero residen en archivos independientes. La unificación empaqueta ambos espacios de features junto con los metadatos necesarios para la evaluación (género musical, nombre de la canción, artista) en un único archivo que constituye la entrada para la etapa de clustering.

El proceso de unificación incluye una batería de verificaciones de integridad cruzada que confirman la consistencia entre los distintos componentes:

\begin{itemize}[leftmargin=2em]
    \item Los 17\,964 \texttt{track\_id} del dataset seleccionado coinciden exactamente con los almacenados durante la vectorización, lo que garantiza que el embedding semántico de la posición $i$ corresponde a la misma canción que las features musicales de la posición $i$.

    \item Los embeddings semánticos mantienen norma L2 unitaria (media = 1.0000, desviación estándar = 0.0000), confirmando que la re-normalización posterior al chunking se preservó correctamente.

\end{itemize}

\section{Clustering Multimodal}
\label{sec:clustering-multimodal}

El clustering sobre las representaciones del dataset cumple dos roles diferenciados en este trabajo. El primero es analítico: verificar que los embeddings semánticos y las features musicales contienen estructura interna real y no son indistinguibles de ruido uniforme. Sin esta verificación, cualquier sistema de recomendación construido sobre estas representaciones operaría sobre una premisa no validada. El segundo rol es funcional: evaluar si las agrupaciones detectadas tienen granularidad suficiente para servir como mecanismo de recomendación alternativo o complementario a la búsqueda directa por vecinos más cercanos.

La evaluación se organiza en dos pasos secuenciales. Primero, el estadístico de Hopkins determina si los datos exhiben tendencia al agrupamiento. Segundo, una comparación multi-algoritmo identifica la mejor configuración de clustering para cada espacio y cuantifica la complementariedad entre modalidades.

El análisis contempla cuatro espacios de representación: el espacio semántico original de 384 dimensiones, una proyección UMAP de este espacio a 30 dimensiones, el espacio musical de 13 dimensiones, y el espacio concatenado de 397 dimensiones. Los tres primeros reciben el análisis completo (test de Hopkins y comparación multi-algoritmo). El espacio concatenado se evalúa únicamente en el test de Hopkins, ya que las 384 dimensiones semánticas dominan numéricamente sobre las 13 musicales, diluyendo la contribución de estas últimas en cualquier algoritmo basado en distancia.

\subsection{Evaluación de Tendencia al Agrupamiento}
\label{subsec:evaluacion-hopkins}

Antes de aplicar algoritmos de clustering, es necesario verificar que los datos presentan estructura interna. El estadístico de Hopkins compara las distancias entre los puntos reales y sus vecinos más cercanos contra las distancias equivalentes generadas desde una distribución uniforme de referencia. Un valor cercano a 0.5 indica que los datos son indistinguibles de ruido aleatorio; valores superiores a 0.7 se interpretan como tendencia significativa al agrupamiento \parencite{lawson_1990_hopkins}.

La evaluación se ejecuta sobre los cuatro espacios con 30 iteraciones y 100 muestras por iteración, generando intervalos de confianza al 95\%. Un detalle técnico relevante es la distribución de referencia empleada: para el espacio semántico original, cuyos embeddings están normalizados a norma L2 unitaria y por tanto residen en la superficie de una hiperesfera, los puntos uniformes de referencia se generan sobre la hiperesfera (vectores normales multivariados re-normalizados) y la distancia se calcula mediante similitud coseno. Para los demás espacios, los puntos de referencia se generan en el hipercubo con distancia euclídea estándar.

\input{tables/hopkins_results}

El Cuadro~\ref{tab:hopkins_results} y la Figura~\ref{fig:hopkins_results} presentan los resultados. Los cuatro espacios superan el umbral de 0.7, confirmando que ambas representaciones contienen estructura real. El espacio semántico original exhibe un valor de Hopkins notablemente alto ($H = 0.9472 \pm 0.0028$), lo que indica que los embeddings de letras capturan agrupaciones temáticas pronunciadas. El espacio musical, con $H = 0.8298 \pm 0.0103$ en 13 dimensiones, muestra una estructura más moderada pero igualmente significativa. El espacio concatenado obtiene el valor más bajo ($H = 0.7415$), coherente con la expectativa de que la dimensionalidad desproporcionada del componente semántico diluye la contribución del componente musical cuando ambos se combinan directamente.

La proyección UMAP a 30 dimensiones del espacio semántico produce un Hopkins de 0.9923, superior al del espacio original. Este resultado es informativo respecto a una preocupación metodológica sobre el uso de Hopkins en alta dimensionalidad: \textcite{aggarwal_2001_dimensionality} documentan que en espacios de muchas dimensiones la diferencia relativa entre la distancia al vecino más cercano y al más lejano tiende a cero, lo que podría inflar artificialmente el estadístico de Hopkins. Si este efecto estuviera presente, la proyección a 30 dimensiones (que mitiga la concentración de distancias) debería producir un valor \textit{menor}, no mayor. El resultado inverso confirma que el valor de 0.9472 en 384 dimensiones es conservador: UMAP concentra la estructura en menos dimensiones, lo que facilita su detección, pero no la inventa.

\subsection{Selección de Algoritmo y Configuración}
\label{subsec:seleccion-algoritmo}

Con la tendencia al agrupamiento confirmada, el paso siguiente es determinar qué algoritmo y qué número de clusters produce la partición de mayor calidad en cada espacio. Se evalúan tres familias de algoritmos (K-Means++, Ward y HDBSCAN) que representan, respectivamente, partición por centroides, aglomeración jerárquica por varianza y agrupación por densidad. K-Means++ y Ward se ejecutan con $K \in \{5, 6, 7, 8\}$; HDBSCAN recibe el parámetro \texttt{min\_cluster\_size} $\in \{50, 100, 200, 300, 500\}$ y determina el número de clusters automáticamente.

La amplitud de estos rangos responde al propósito del clustering en este trabajo: no maximizar la separación a cualquier costo, sino obtener en cada espacio una partición representativa y de granularidad comparable sobre la cual medir la complementariedad cross-modal. El rango de $K$ se acota inferiormente cerca de los seis géneros del catálogo, una granularidad por debajo de la cual la partición degenera en un corte binario poco informativo para la comparación entre modalidades. Un barrido de control que extendió la búsqueda hasta $K = 20$ y redujo el piso de \texttt{min\_cluster\_size} hasta 20 confirmó la adecuación de los rangos: ninguna configuración de mayor granularidad mejora la calidad en ningún espacio, ya que los valores altos de $K$ fragmentan los datos en micro-clusters por debajo del 1\% que el filtro de degeneración descarta; y la mejor partición del espacio semántico UMAP, la única empleada en el análisis posterior, resultó óptima sobre la totalidad del rango ampliado. En los espacios de estructura más difusa (musical y semántico de 384 dimensiones), las particiones más gruesas que el piso adoptado alcanzan un Silhouette ligeramente superior, coherente con su baja granularidad, pero no modifican ninguna conclusión de esta sección.

La selección de la mejor configuración se basa en la triangulación de dos métricas internas: el coeficiente de Silhouette en su variante \textit{macro-averaged} (promedio por cluster) y el índice de Davies-Bouldin. \textcite{chicco_2025_silhouette_db} demuestran empíricamente que estas dos métricas exhiben 100\% de consistencia con el índice de Rand ajustado como métrica externa, frente al 70\% del índice de Calinski-Harabasz. La variante macro del Silhouette se adopta como métrica primaria para evitar la inflación que produce la variante micro ante distribuciones degeneradas: un cluster que contenga el 99\% de los datos domina el promedio global y puede producir valores artificialmente altos. Complementariamente, se descartan dos tipos de configuración no representativa: las que generan algún cluster con menos del 1\% del dataset (degeneradas) y las que clasifican como ruido a más del 50\% de las canciones. Este segundo criterio es necesario porque un algoritmo basado en densidad como HDBSCAN puede obtener un Silhouette alto agrupando únicamente el subconjunto más denso del espacio y descartando la mayoría de los puntos como ruido; ese Silhouette se calcula sobre una fracción minoritaria del catálogo y no refleja la estructura global, por lo que una partición de ese tipo no constituye una base válida de comparación.

\input{tables/clustering_best_configs}

El Cuadro~\ref{tab:clustering_best_configs} presenta la mejor configuración identificada para cada espacio. Los resultados revelan tres hallazgos principales.

En primer lugar, el espacio semántico original de 384 dimensiones produce un clustering muy pobre (Silhouette macro de 0.0362) a pesar de su alto Hopkins. La estructura existe (los puntos no están distribuidos uniformemente) pero no se traduce en clusters bien separados: las regiones de alta densidad se solapan gradualmente en lugar de estar separadas por fronteras nítidas. Este fenómeno es una manifestación directa de la maldición de la dimensionalidad, en 384 dimensiones, las distancias entre puntos se comprimen y los algoritmos de partición pierden capacidad discriminativa. El contraste entre un Hopkins alto y un Silhouette bajo no es contradictorio: ambas métricas miden propiedades distintas, afectadas de forma diferencial por la dimensionalidad. Hopkins compara la distancia al vecino más cercano contra una referencia uniforme y detecta estructura aun cuando las distancias absolutas estén concentradas; el Silhouette, en cambio, exige que las distancias inter-cluster superen significativamente a las intra-cluster, condición que la concentración de distancias aplana. Un Silhouette bajo en alta dimensionalidad no implica entonces ausencia de estructura, sino únicamente que los algoritmos de partición no logran capturarla en ese espacio, como confirma su recuperación al reducir la dimensionalidad. HDBSCAN resulta completamente inutilizable en este espacio, clasificando el 100\% de los puntos como ruido para cualquier \texttt{min\_cluster\_size} $\geq 100$.

En segundo lugar, la proyección UMAP a 30 dimensiones transforma radicalmente la calidad del clustering semántico. HDBSCAN identifica 3 clusters de tamaños muy desiguales (15\,340, 1\,739 y 237 canciones) con un Silhouette macro de 0.9137 y apenas un 3.6\% de puntos (648 canciones) clasificados como ruido. Esta mejora confirma que la estructura detectada por Hopkins en 384 dimensiones es real pero inaccesible para los algoritmos de clustering sin reducción dimensional previa. Los intentos de forzar más clusters en este espacio (tanto con K-Means como con Ward para $K \geq 6$) producen configuraciones degeneradas: el algoritmo mantiene los 2--3 grupos naturales y fragmenta los bordes en micro-clusters espurios de pocas decenas de canciones. Con K-Means $K = 5$ (la granularidad máxima sin degeneración), el Silhouette desciende a 0.5263 y los clusters siguen siendo muy desiguales (uno con 9\,104 canciones y otro con 237).

En tercer lugar, el espacio musical de 13 dimensiones presenta una estructura difusa y de baja granularidad. A diferencia del espacio semántico, su baja dimensionalidad descarta la maldición de la dimensionalidad como causa: las features acústicas se distribuyen de forma gradual, sin un corte nítido donde, por ejemplo, ``alta energía'' termina y ``baja energía'' empieza, lo que produce fronteras difusas entre grupos independientemente del algoritmo utilizado. La mejor partición de cobertura total dentro del rango de granularidad adoptado es K-Means $K = 5$, con un Silhouette macro de 0.1028 y cinco grupos que reparten la totalidad de las 17\,964 canciones (entre 803 y 6\,441 canciones por grupo). HDBSCAN, en cambio, no produce una partición representativa del espacio: aísla únicamente dos pequeños bolsones densos (885 y 1\,986 canciones) y clasifica como ruido al 84\% del catálogo. Su Silhouette aparentemente superior (0.1991) se calcula solo sobre ese 16\% agrupado, por lo que la configuración se descarta por el criterio de cobertura. El bajo Silhouette de la mejor partición de cobertura total confirma que la granularidad natural del espacio musical es baja.

\subsubsection*{Complementariedad cross-modal}

Para justificar la fusión multimodal, es necesario demostrar que los dos espacios capturan información diferente. Si los clusters semánticos y musicales fueran equivalentes, la fusión no aportaría valor. La Información Mutua Normalizada (NMI) entre las asignaciones de cluster de ambas modalidades cuantifica este solapamiento: un NMI cercano a 1 indica que ambas particiones dicen lo mismo, mientras que un NMI cercano a 0 indica complementariedad total. Se adopta un umbral de $0{,}15$ como criterio: un valor por debajo de ese umbral indica independencia sustancial entre las modalidades.

\input{tables/cross_modal_nmi}

El Cuadro~\ref{tab:cross_modal_nmi} reporta el NMI calculado entre el mejor clustering semántico (la proyección UMAP con HDBSCAN, $K = 3$) y la mejor partición musical de cobertura total (K-Means, $K = 5$). Ambas particiones se eligen sobre agrupamientos con estructura real y cobertura del catálogo completo, de modo que el NMI mide complementariedad genuina y no el solapamiento entre particiones arbitrarias. El valor obtenido, $0.0298$, se ubica muy por debajo del umbral ($0{,}0298 \ll 0{,}15$) y es cercano a cero, lo que indica una complementariedad prácticamente total: las agrupaciones temáticas que emergen del análisis de letras no se corresponden con las agrupaciones sonoras que emergen de las features acústicas. Este resultado es esperable: una canción acústica y melancólica puede compartir temática de desamor con una balada electrónica, mientras que dos canciones de alta energía pueden tratar temas completamente distintos. La complementariedad casi total entre ambas modalidades constituye la justificación empírica para la fusión multimodal que se implementa en la Sección~\ref{sec:sistema-hibrido}.

\subsubsection*{Implicaciones para el sistema de recomendación}

Los resultados del clustering revelan que la granularidad natural de los datos es baja: 3 grupos en el espacio semántico y, en el musical, una estructura difusa que la mejor partición de cobertura total resuelve en 5 grupos de baja cohesión. En ambos casos los clusters agrupan miles de canciones cada uno (hasta 6\,441 en el musical), de modo que la pertenencia a un mismo cluster es una señal demasiado débil para generar recomendaciones precisas (equivaldría a recomendar una fracción sustancial del catálogo). Forzar una granularidad mayor produce particiones degeneradas o de baja calidad.

Esta observación determina la estrategia de recomendación para la Sección~\ref{sec:sistema-hibrido}: el mecanismo primario será la búsqueda directa de los $K$ vecinos más cercanos (\textit{k-NN}) mediante distancia coseno, que opera a nivel de canción individual y no requiere una partición previa.

\section{Sistema de Recomendación Híbrido}
\label{sec:sistema-hibrido}

El análisis de clustering de la sección anterior estableció que la granularidad natural de ambos espacios es demasiado baja para servir como mecanismo de recomendación: con apenas 3 grupos semánticos y 5 musicales, todos de gran tamaño, la pertenencia a un mismo cluster no discrimina con la finura que requiere la recomendación canción a canción. En contrapartida, la búsqueda directa de los $K$ vecinos más cercanos (k-NN) opera a nivel de canción individual, produciendo un ranking continuo de similitud sobre las 17\,963 canciones restantes del dataset. Esta sección describe el diseño del sistema de recomendación que combina los dos espacios mediante k-NN con fusión tardía de scores.

El sistema resuelve cuatro decisiones concretas: qué métrica usar en cada espacio, cómo combinar los scores de ambas modalidades en uno solo, cómo elegir el peso relativo entre componentes, y cómo evaluar la calidad de las recomendaciones producidas. Las dos primeras se resuelven en la subsección de estrategia de fusión; la tercera, en la de optimización de pesos; la cuarta, en las subsecciones de evaluación y de métricas complementarias. Una decisión adicional, cómo se depura la lista final que se presenta al usuario, se aborda en la subsección de deduplicación.

% ---------------------------------------------------------------------------
% SUBSECCIÓN 5.7.1 — Estrategia de Fusión
% ---------------------------------------------------------------------------
\subsection{Estrategia de Fusión}
\label{subsec:fusion}

El sistema adopta la \textit{fusión tardía}, en lugar de concatenar ambas representaciones en un único vector de 397 dimensiones y operar sobre el espacio combinado, calcula una similitud independiente en cada espacio y las combina en un único score mediante la combinación lineal ponderada de la Ecuación~\ref{eq:fusion-tardia}.

La elección se apoya en el análisis de Hopkins sobre el espacio concatenado, arrojó el valor más bajo de los cuatro espacios evaluados ($H = 0{,}7415$): al concatenar, las 384 dimensiones semánticas dominan numéricamente sobre las 13 musicales y diluyen la contribución del componente musical en cualquier cálculo de distancia sobre el espacio combinado. La fusión tardía evita esa dominancia, preserva la contribución equilibrada de cada modalidad y permite ponderarlas explícitamente con un único parámetro; además, al operar cada componente por separado, mantiene ambos módulos independientes, de modo que cada uno puede evaluarse y ajustarse sin recomputar el otro.

Aplicada a este sistema, la Ecuación~\ref{eq:fusion-tardia} toma como componentes la similitud semántica $s_{\text{sem}}$ y la musical $s_{\text{mus}}$, con $\alpha$ como peso del componente semántico. Su aplicación exige que ambas similitudes sean comparables: que estén en la misma escala numérica y compartan la convención de que un valor mayor indica mayor similitud. Las métricas elegidas para cada espacio son distintas, por las propiedades de las representaciones correspondientes, y se describen a continuación.

\subsubsection*{Similitud en el espacio semántico}

Como los embeddings semánticos producidos en la Sección~\ref{sec:componente-semantico} ya se entregan L2-normalizados por el pipeline de vectorización, la similitud coseno definida en la Sección~\ref{subsec:knn-recuperacion} se reduce en este espacio al producto punto $s_{\text{sem}}(q, c) = \mathbf{v}_q \cdot \mathbf{v}_c$. La implementación aprovecha esa equivalencia para calcular todas las similitudes de una sola vez: apilando los 17\,964 embeddings en la matriz $\mathbf{V}$ de dimensiones $17\,964 \times 384$, la matriz completa se obtiene con una única multiplicación matricial $\mathbf{S}_{\text{sem}} = \mathbf{V}\mathbf{V}^T$.

El rango de similitud observado es $[0{,}69, 1{,}00]$: los valores negativos que el coseno admite en teoría no aparecen porque todas las entradas son letras de canciones y sus vectores apuntan en direcciones parecidas, tal como anticipa la Sección~\ref{subsec:knn-recuperacion}.

\subsubsection*{Similitud en el espacio musical}

Las features musicales están estandarizadas mediante \textit{z-score}, no L2-normalizadas: sus magnitudes son variables y codifican cuán extremas son las características de cada canción. Aplicar el coseno en este espacio descartaría esa información de magnitud, tratando como equivalentes dos canciones con el mismo perfil relativo pero distinta intensidad. Por eso la similitud musical se deriva de la distancia euclídea entre los vectores de 13 features y se convierte en una similitud acotada en $[0, 1]$ mediante el kernel gaussiano, paso necesario para que el score musical sea comparable con el semántico en la fusión.

El parámetro $\sigma$ del kernel se fija con la heurística de la mediana: sobre una muestra aleatoria de 5\,000 canciones, la mediana resultante fue $\sigma = 4{,}7634$.

Las matrices de similitud resultantes reflejan las distintas propiedades de cada métrica: la matriz semántica produce valores en el rango $[0{,}6912,\; 1{,}0000]$ con media $0{,}8702$, mientras que la matriz musical, tras la conversión por kernel, produce valores en $[0{,}0026,\; 1{,}0000]$ con media $0{,}5887$. La distribución del score musical es considerablemente más amplia que la del semántico, lo que refleja que la distancia euclídea preserva mayor capacidad discriminativa global en 13 dimensiones que la similitud coseno en 384 dimensiones.

% ---------------------------------------------------------------------------
% SUBSECCIÓN 5.7.2 — Optimización de Pesos
% ---------------------------------------------------------------------------
\subsection{Optimización de Pesos}
\label{subsec:optimizacion-pesos}

Con las similitudes semántica y musical definidas como se describió en la subsección anterior, resta determinar el peso $\alpha$ que produce las recomendaciones de mayor calidad según un criterio de evaluación. La estrategia elegida es \textit{grid search}: evaluar sistemáticamente el desempeño del sistema para un conjunto discreto de valores de $\alpha$ y seleccionar el que maximiza la métrica de calidad primaria.

Se emplea grid search por tres razones. En primer lugar, $\alpha$ es un parámetro único y acotado en $[0, 1]$, lo que hace viable una búsqueda exhaustiva con granularidad suficiente. En segundo lugar, la métrica de calidad (Precision@K) se calcula sobre el ranking de recomendaciones, que resulta de ordenar las canciones por score. Pequeños cambios en $\alpha$ no alteran ese orden hasta que dos canciones se cruzan, momento en que la métrica salta de forma abrupta: es una función escalonada de $\alpha$, sin una pendiente que los métodos de optimización por gradiente puedan seguir. El grid search evita ese problema al no requerir derivadas. En tercer lugar, el grid search permite visualizar la sensibilidad completa del sistema a $\alpha$, información que queda documentada y facilita la interpretación de resultados.

La grilla evaluada consta de 21 valores equiespaciados: $\alpha \in \{0{,}00,\; 0{,}05,\; 0{,}10,\; \ldots,\; 0{,}95,\; 1{,}00\}$. Para cada valor se ejecuta el siguiente procedimiento:

\begin{enumerate}[leftmargin=2em]
    \item Combinar las matrices de similitud pre-computadas según la Ecuación~\ref{eq:fusion-tardia}: $\mathbf{S} = \alpha \mathbf{S}_{\text{sem}} + (1 - \alpha) \mathbf{S}_{\text{mus}}$.
    \item Para cada canción del dataset, tomar como query y seleccionar las $K$ canciones con mayor score en la fila correspondiente de $\mathbf{S}$, excluyendo la propia query.
    \item Evaluar la calidad de las recomendaciones generadas mediante la métrica Precision@K con distintos valores de $K$.
\end{enumerate}

\subsubsection*{Ground truth: el género como proxy de relevancia}

La evaluación de recomendaciones requiere definir cuándo una recomendación es \textit{relevante} respecto a una query. En ausencia de evaluaciones humanas a gran escala sobre el dataset, se adopta el género musical como \textit{proxy} de relevancia: una recomendación se considera relevante si comparte etiqueta de género con la query. Esta elección se declara explícitamente por sus limitaciones conocidas: las etiquetas son asignaciones subjetivas de la industria con acuerdo inter-evaluador del orden del 70-80\%, no son mutuamente excluyentes (una canción puede pertenecer a varios géneros) y capturan una única dimensión de similitud musical. En consecuencia, un sistema puede producir recomendaciones excelentes en términos subjetivos que crucen géneros y queden marcadas como no relevantes, y viceversa.

Bajo esta convención la función indicadora de relevancia vale 1 cuando la recomendación comparte género con la query ($g_i = g_q$) y 0 en caso contrario. Sus valores extremos sirven de referencia para interpretar los resultados: un sistema que siempre recomienda canciones del género de la query alcanza Precision@K unitaria, mientras que uno que recomienda al azar obtiene aproximadamente la proporción del género dominante en el dataset, que fija el piso de referencia.

\subsection{Deduplicación de la Lista de Recomendación}
\label{subsec:deduplicacion}

El catálogo contiene la misma grabación registrada más de una vez con identificadores distintos, un fenómeno habitual en las colecciones musicales, donde una canción figura simultáneamente en el álbum original, en ediciones posteriores y en discos recopilatorios, y que en este conjunto de datos se acentúa porque las canciones se recolectaron desde múltiples \textit{playlists}. De las 17\,964 canciones, 1\,901 son repeticiones de otra grabación ya presente, de modo que el catálogo comprende 16\,063 grabaciones únicas.

Estas repeticiones no se eliminan del conjunto de datos ni de la evaluación, por una razón metodológica. Cuando el sistema sitúa una copia exacta de la consulta entre las canciones más similares, lo hace correctamente: una grabación idéntica es, por definición, lo más parecido posible a la consulta. Su aparición es, por tanto, una comprobación de que la medida de similitud opera como se espera, y no un defecto a corregir. En consecuencia, las métricas de las subsecciones anteriores se calculan sobre las listas de vecinos sin filtrar, que reflejan el comportamiento directo de la similitud.

Recomendar dos veces la misma canción, en cambio, no aporta valor a un usuario. Por eso, al construir la lista final que este recibiría, se aplica un paso de deduplicación en post-procesamiento: se recuperan más candidatos que los $K$ requeridos, se descarta la propia grabación de la consulta y se conserva una sola entrada por grabación, completando la lista con los siguientes candidatos hasta reunir $K$ canciones distintas. Dos entradas se consideran la misma grabación cuando coinciden en título e intérprete normalizados, o cuando sus vectores son prácticamente idénticos en ambas modalidades (similitudes semántica y musical cercanas a la unidad), criterio que captura las copias registradas con títulos ligeramente distintos. Las piezas que no son la grabación original, como remasterizaciones, ediciones en vivo, versiones acústicas, \textit{covers} o traducciones, no se consideran duplicados y se conservan, ya que difieren de forma apreciable en el vector musical y constituyen grabaciones legítimamente distintas. El efecto de este paso sobre consultas concretas se ilustra en el Capítulo~\ref{ch:resultados}.

\paragraph{Diversidad intra-lista.} La ILD (Ecuación~\ref{eq:ild}) se computa en dos variantes, una por espacio de representación: la \textit{ILD semántica} emplea la distancia coseno $d(u, v) = 1 - s_{\text{coseno}}(u, v)$ sobre los embeddings, y la \textit{ILD musical} la distancia euclídea sobre las features estandarizadas. Al $\alpha$ óptimo, la ILD semántica es $0{,}0957$ y la ILD musical, $2{,}6357$.

Como la ILD carece de escala absoluta (Sección~\ref{subsec:evaluacion-recomendaciones}), estos valores solo cobran sentido frente a un punto de referencia medido con la misma distancia. Se adopta como referencia la diversidad de un \textit{recomendador aleatorio}, para cada una de las 17\,964 canciones del catálogo se genera una lista de diez canciones muestreadas de forma uniforme y sin repetición del propio catálogo; sobre cada lista se computa su ILD con las mismas dos distancias que emplea el sistema, y el promedio sobre las 17\,964 listas constituye el piso esperado cuando no interviene ningún criterio de similitud. Este baseline arroja una ILD musical de $4{,}92$ y una semántica de $0{,}13$.

Es decir, las listas son más cohesivas que una selección al azar en los dos espacios, lo que confirma que tanto el componente semántico como el musical agrupan canciones afines en lugar de producir listas arbitrarias.

\paragraph{Cobertura del catálogo.} El sistema alcanza un $95{,}54\%$: 17\,162 canciones distintas aparecen como recomendación para al menos una consulta, y solo 802 (el $4{,}46\%$) no se recomiendan nunca.

Una cobertura tan alta indica que el sistema no concentra sus sugerencias en un núcleo reducido de canciones, sino que expone casi todo el catálogo. Como cada canción es vecina cercana de algún conjunto de consultas, casi todas encuentran ocasión de ser recuperadas. La ausencia de un sesgo severo de popularidad es una propiedad deseable, pues evita el círculo en que unos pocos ítems muy expuestos acaparan las recomendaciones mientras el resto del catálogo permanece invisible para el usuario.

Todos los géneros superan el 93\% de cobertura y la variación entre ellos es de menos de cuatro puntos absolutos, lo que descarta un sesgo severo de popularidad por género.
